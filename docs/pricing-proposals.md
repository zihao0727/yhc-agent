# 方案驱动报价

## 工作流程

1. 程序优先提取文件中的清单，保留项目、数量、单位和原始位置。复杂文件沿用订单独立的隔离 Python 工作区。
2. 对当前项目准备资料包：原文来源编号、成品价格、材料加工成本分项、组合参考价、已编码规则及有效规则原文。
3. Agent 拆分实际部件，明确计量方法，提交简洁计算方案。常见计量由程序生成公式，特殊工程量可以使用受限算术脚本。
4. 服务端绑定真实单元格和当前成本版本，用 Decimal 计算，检查单位、来源、重复费用、部件覆盖及规则适用。
5. 校验失败时保留完整方案和版本，Agent 只修正失败字段并重新计算。资料不足则记录具体问题，继续其他项目。
6. 校验通过保存待审核报价。对话修改尺寸、数量后重算；材质、厚度等变化使旧成本方案失效，必须重新核价。

## 本次改变

- 默认启用 `submit_pricing_plan` / `repair_pricing_plan`，减少模型输出大段原文引文、索引和重复公式导致的格式错误。
- 来源编号由程序分配；模型不能伪造单元格文字或把其他项目的来源用于当前项目。
- `basis` 区分原文事实、推导值和暂定假设。数值单位换算需要标为推导；原文未写明的材质牌号不能标为事实。
- 成本候选分别准备成品、材料加工、组合参考，避免几千条记录中只检索到发光字成品价。
- 材料加工原表可分别引用材料费、工序一和工序二，绑定对应 H/E/G 单元格及当前价格版本。空费用不默认零；总价和分项不能重复计费。
- 工艺分项不能冒充另一种工艺的匹配价；使用类比估价时必须列明差异、费率和理由并接受审核。
- 原文明确有加工要求时，材料小计不能作为完整成品报价保存；面层和背板需要分别覆盖，丝印、盲文及磁铁等明确要求须说明费用归属。
- 引擎诊断自动转换为简洁方案的修改路径，保留内部路径供追溯，避免模型在两个字段体系间反复出错。
- 模型响应多次异常只暂挂受影响项目，其他项目继续；新一轮恢复保留方案，但重新给出该项的修复机会。
- 对话可定位 Agent 方案中拆出的部件。尺寸修改使脚本使用新参数重算，不沿用旧金额。

## 能力边界

程序可以验证金额和资料引用，但不能自动证明每一种工艺解释和暂估费率都符合实际生产。
不承诺任意文件都能自动形成完整商业报价。缺失成本、单字尺寸、部件工程量或含税安装口径时必须明确提示。

## 运行时自修复

`AGENT_RUNTIME_RECOVERY=true`默认启用，`AGENT_RUNTIME_REPAIR_ATTEMPTS=3`限制单个故障的修复次数。框架不为每种新错误添加报价特例：失败调用按当前真实工具契约生成`self_repair`，包含失败编号、原调用、字段诊断、接口schema和已验证的同类处理提示。

Agent可以用`repair_failed_tool`提交修正后的完整参数，或选择其他允许工具完成同一目的。文件处理仍可编写和修正隔离脚本，关联`previous_artifact`并重新接受独立校验。重放在SQL保存点内执行：原始需求、人工输入和其他项目发生变化，或工具/报价校验失败时回滚。原样调用、过期故障编号、变更后的需求及跨项目修复被拒绝；手动停止优先于继续执行。

上下文增强模块出现字段/类型异常时，恢复上下文保留原始需求及受限工具，模型可继续核对来源和编制方案；不会绕过原计价引擎。技术故障不自动变成客户缺资料，不能把未经验证的数字当已报价金额。

成功重放或通过替代工具保存有效报价后，`_workspaces/runtime-repairs`记录工具、契约指纹、改动字段路径和替代工具名。跨任务提示不保存客户值、数量、单价、来源编号或脚本文本；契约改变后不引用旧提示，不自动复制旧修复参数。修复状态和调用保存在SQL，继续任务时保留可用状态并重新核验。

这些修复在运行时执行，无须为每次参数、工具路径或隔离脚本问题修改服务代码和重启。任意底层Python缺陷不保证能自动改好；不能绕行且不能通过原引擎验证时，保留诊断并只暂挂受影响项，仍需在隔离环境验证代码变更后发布。系统不在运行中任意改写主程序、价格库或审核规则。
暂估费率、推导参数、新拆部件仍需审核；未完成行不会按零元汇总为完整报价。

文件解析脚本运行于无网络、只读输入、限制资源的 Docker 环境；计价脚本只执行有限的算术和断言。
Docker 不可用时报告环境问题，不回退到宿主机运行模型代码。现有 Python 工作区与可复用适配器机制继续使用。

## 配置与审计

- `AGENT_COMPACT_PLANS=true`：默认启用简洁方案。设为 false 可回退旧工具接口，已保存报价无需迁移。
- `AGENT_RESPONSE_MAX_TOKENS=10000`：单次模型输出容量，不是整单用量额度。
- `AGENT_PRICING_CONCURRENCY=4`：后台报价默认最多同时请求 4 个独立项目，范围 1–16；设为 1 恢复逐项请求。资料提取及跨文件核对沿用原流程。
- 并发线程只调用模型，不共享数据库会话。协调器逐项校验并提交结果，每次提交后发布 Redis 进度；每个回复只能操作分配给它的项目。全部项目处理完后才允许整单汇总。
- 项目上下文、失败方案、重试时间和用量分别记录。连接失败使用逐项指数退避；429 至少等待一秒；达到重试上限只暂挂受影响项目。密钥、余额或配置错误暂停运行。
- 中途修改项目或补充对话后，过时回复不执行。停止后已保存金额保留，已发送请求等待返回或超时并记录用量，回复中的工具不再执行；继续时复用已保存项目。
- 时间切片和总用量上限阻止发送下一批请求；已发送的一批先收尾，因此实际用量可能超过额度，最多受同时在途请求数量及单次响应容量影响。并发减少等待，不降低模型计费用量。
- 全局、单项 token 额度仍使用既有配置，值为 0 表示不启用相应额度。单项耗时、重复失败等保护保留。
- 方案、资料包、编译结果、校验结果保存在订单工作区 `pricing/<line_id>/<hash>.json`；SQL 运行记录保存修复版本和逐项进度。
- 接口执行记录可查看计算结果；报价详情显示成本分项和原表位置，编辑器可选择完整单价或原表分项。
- 订单原始输入变化后旧方案补丁失效，防止对过时的资料继续局部修改。

## 验证

在 backend 目录运行：

```powershell
../.venv/Scripts/python.exe -m pytest -q
../.venv/Scripts/python.exe -m scripts.verify_pricing_order --job 20 --turns 12 --workers 4 --output ../.runtime/pricing-acceptance-final.json
```

第二条命令调用已配置的真实模型并产生模型费用，仅试算、不修改业务订单和原报价。
验收复用已保存金额时标记 `origin=existing_saved_estimate`。新增方案和修复记录保留在报告中。
`priced_review` 只表示通过程序校验的待审核金额；`needs_input` 表示明确的成本或资料问题；
`technical_failure` 表示执行错误或限定轮次内未完成，不能当作业务资料缺失。
可用 `--indices 0,5,12` 对指定的零起始行号单独复验。
`--resume-from` 可以合并同订单、同输入版本的已验收结果，并恢复所选项目的失败方案继续修正。

2026-10-13 的订单20最终验收覆盖85项：3项有待审核金额（其中1项沿用已有估价），
82项明确列出成本或资料问题，0项执行未完成。仅算材料的中间结果在补充覆盖校验后没有被作为成品报价接受。
因此，当前已实现方案编制、修复、程序计算及追问的工作闭环，但该实单仍未形成完整商业报价。

## 2026-10-19 执行效率优化

- 同一次并发调度只计算一次整单进度，供本批各项目构建上下文。原文页面也仅在本批内复用，来源登记、图纸定位及客户原表价格参考共享读取结果。批次结束即释放，不跨批缓存计算金额或价格候选；下一批重新读取当前需求与价格。
- 并发模式由各项目在发送前构建自己的上下文，协调器不再额外构建、压缩一份不会发送的整单上下文。人工修改后的旧回复仍按输入指纹拒绝执行。
- 模型上下文省略资料对象的空字段，保留零、否、未知值和数组位置。空字段省略不代表已确认或无需计费；数据库原始资料和审计不变。
- 简洁方案修复保留当前版本、完整可编辑方案和诊断，不再同时发送重复的引擎中间方案。没有简洁方案的兼容路径仍保留原失败方案。
- 历史压缩以文本大小计算，不把图片的 Base64 传输长度当作文本。压缩只移除旧的完整消息组，保留最近一组完整工具调用、全部对应结果及后续提示；静态资料包较大时也不丢弃刚返回的字段诊断。模型响应格式失败后，下一次本项请求明确要求缩小输出和修正字段。
- 没有暂挂项时不重复检查整单是否应结束；存在可继续处理的项目时提前结束该检查。真正交付、保存、批准和导出仍走原有完整校验，不用调度快照代替报价校验。

回归入口：`tests/test_pricing_performance.py`。覆盖同批计算次数、页面读取次数、跨批重新读取、完整工具消息组、原图保留、失败方案诊断和最终报价金额。测试使用模拟模型；实际订单耗时仍受资料复杂度、成本缺项和模型服务影响，不承诺固定提速倍数。
